# Proposal: commitment behavior-clone LoRA recipe (decoder-first, LoRA as sequenced fallback) (2026-10-14)

Type: training recipe (LoRA adapter) + a decode-sweep gate that precedes it. Status: UNAUDITED.

Grounded in the research dossier `Gemma\kb\research\2026-10-14-lora-what-to-train-dossier.md` and the measured priors brief `Gemma\kb\research\_priors_brief.md`. Every claim below is tagged MEASURED-LOCAL (a measured prior), MEASURED/ESTABLISHED (cited external literature in the dossier), or INFERRED (an extrapolation / hypothesis, not a verdict). This file is a hypothesis set to run through `gemma-audit`, not a recommendation.

## The change

Install the "commit-fast motion" — once the fault is localized, emit `edit_file` instead of another grep/read/pytest — into the FIXED `gemma-4-31b-it-qat-w4a16-ct` agent. The target skill is COMMITMENT / stop-searching-after-locating, NOT edit-anchor discipline and NOT a knowledge/capability LoRA (dossier §1; priors A1, A3).

Critical sequencing, straight from the dossier verdict (§1, §2, §8): **do NOT train a LoRA first.** The behavior "stop searching, commit the edit" is predominantly DECODING-shaped, so the first gate is a zero-GPU decode/budget sweep. The commitment LoRA is the **sequenced fallback**, justified ONLY if a pre-registered decode sweep fails to move commitment on a by-task holdout (dossier §1 "if and only if"; §8 Arm 1 → Arm 2). Framed this way because the dossier concluded commitment timing is in LoRA's teachable class but the cheapest, highest-evidence channel is the decoder, and our own data already lit the decoder up (priors §B: `freq_penalty 0.4` killed the repeat-loop; a reserve-tail made every task reach an edit).

Concretely this proposal is two gated stages, one change at a time:

1. **Stage A (do first; hours, no GPU) — decode/budget sweep.** Sweep one dial at a time on the dev-task by-task holdout via `eval_hf_adapter.py`: `frequency_penalty` (around the 0.4 that already worked, priors §B), `presence_penalty`, `temperature`/`top_p` (lower-entropy nucleus to curb loops, MEASURED/ESTABLISHED Holtzman 1904.09751 per dossier §2), and the get_status reserve-tail / edit-shape knob (dossier §8 Arm 1). If Stage A clears the bar, the LoRA is unnecessary for commitment — report that as the result and stop.

2. **Stage B (ONLY if Stage A fails its bar) — commitment behavior-clone LoRA.** A "motion LoRA" for the agent's turn sequence (MotionLoRA analogy, MEASURED/ESTABLISHED AnimateDiff 2307.04725 per dossier §3/T15), trained on self-distilled passing commit-fast trajectories with the full anti-v2 safe-template prescription below (dossier §5d).

## Rationale

(a) SKILL — confirmed, with the honest fork stated. COMMITMENT is the binding failure: the model LOCATES the gold file then burns the budget on grep/read/pytest without ever calling `edit_file` (MEASURED-LOCAL A1; v2 forensic: 3/5 tasks made 0 edit attempts, priors C2). Edit-anchors are a non-problem the harness already forgives (MEASURED-LOCAL A2), and v2 was the WRONG LoRA, not proof the LoRA path is dead (A3). But the dossier does NOT lead with "train a LoRA." It concludes commitment is predominantly decoding-shaped and must be falsified on the decoder first (dossier §1, §2 reconciliation; §8 Disagreement A). This proposal therefore LEADS with the decode route and marks the LoRA as the explicit fallback — stated honestly per the research verdict, not softened into a pro-LoRA story.

(b) TRAINING-DATA RECIPE (Stage B). Self-distilled passing trajectories from PUBLIC GitHub issues — the host-blessed, forbidden-list-safe recipe (MEASURED-LOCAL E), which the dossier maps to the published STaR / ReST^EM / SWE-Gym / Toolformer rejection-sampling family proven on machine-verifiable coding tasks (MEASURED/ESTABLISHED, dossier §5a; SWE-Gym 2412.21139 reports up to 19% absolute resolve gains on this task shape).
- **Two-key filter (dossier §5b):** keep a trajectory ONLY if (1) it ends in pytest-pass AND (2) it reaches its first successful `edit_file` within a small call budget with few redundant read/grep cycles (an overthinking-score proxy; Overthinking 2502.08235 shows selecting lower-overthinking trajectories improved resolve ~30% while cutting cost 43%, MEASURED/ESTABLISHED dossier §5b).
- **Count / diversity / cleaning (dossier §4 table, §5d, §3/T1):** few hundred (300–1000) format-consistent examples, diversity prioritized over volume (FireAct 2310.05915: diversity carries the gain), every single row format-correct because at N≈hundreds one malformed row is a large fraction of signal.
- **The exact safe trajectory/template shape that AVOIDS v2's serialization key-collapse (dossier §5c, §5d):**
  - Never hand-serialize tool calls. Build structured messages with `arguments` as a **dict** and let the model's own `apply_chat_template(..., tools=...)` render each argument as its own `key:<|"|>value<|"|>` pair with a template-owned separator. v2's bug was hand-serializing `edit_file`'s two strings as a single blob so the value-delimiter became data and `old_string:` landed in KEY position (INFERRED mechanism consistent with MEASURED C3; dossier §5c).
  - Byte-identical train/serve template: the vLLM Gemma-4 parser output MUST equal the `apply_chat_template` output used to build labels (a template mismatch is foundation-level drift, dossier §5d item 2).
  - Round-trip-validate every row through Gemma's own parser; assert `old_string` AND `new_string` both round-trip byte-equal, with tests whose values deliberately contain `,`, `}`, backtick, `\n` so delimiter-bearing strings always land inside the `<|"|>` span (dossier §5d items 3–4). This mechanical gate would have caught v2.
- **Loss-masking to assistant/tool-call tokens only (dossier §4 lever #1, §5d item 5):** mask the prompt AND all tool-result turns (grep/pytest/file output); train only on assistant turns via TRL `assistant_only_loss` with `{% generation %}` around assistant turns only. Verify the mask is NONZERO and aligned to the `edit_file` payload boundary before any full run (an earlier NULL run gave mean_loss 0.0000 from over-masking, MEASURED-LOCAL D; the mask boundary is the likeliest mechanical C3 cause, INFERRED dossier §4 lever #1).

(c) HYPERPARAMETERS (Stage B start point + ranges, dossier §4 table unless noted):
- **rank r:** start **16** (range 8–64; cap ≤128, MEASURED-LOCAL F). Low rank for a narrow behavior that sits in a low-dimensional subspace (MEASURED/ESTABLISHED Aghajanyan 2012.13255; Biderman 2405.09673 "learns less, forgets less" at low rank).
- **alpha:** **32 (alpha=2r)**, directly fixing v2's under-driven **effective alpha/r=0.5** (r=32, alpha=16 halves the update — the opposite of the convention; MEASURED C4/priors C-header). If rank is swept, use `use_rslora=True` (scales by `alpha/√r`) instead (MEASURED/ESTABLISHED rsLoRA 2312.03732). Note the dossier labels alpha/r=0.5 "dampened, not v2's culprit" (Raschka: 0.5 can be optimal at high r) — so this is a shape fix, not the sole cause.
- **target modules:** all-linear, text decoder only (q/k/v/o + mlp gate/up/down; vision/audio towers excluded). v2's all-linear choice was CORRECT; do NOT retreat to q/v chasing C3 (dossier §4; honors accountability rule 11 — debug execution, don't retreat).
- **LR:** **1e-4** (range 2e-5–2e-4, QLoRA 2305.14314).
- **epochs:** **1**, not 4 — v2 drove loss 0.907→0.262 over 3 epochs on 23 examples (textbook over-fit, MEASURED C4; LIMA 2305.11206 shows strong alignment from a small curated set at few epochs).
- **warmup:** ~3% of steps (min a few steps for tiny runs). **scheduler:** cosine decay.
- **NEFTune:** **OFF** initially; its effect on strict tool-call format is NOT established and embedding noise could hurt an exactly-emitted format — test behind a gate only if over-fit persists (MEASURED/ESTABLISHED NEFTune 2310.05914; dossier §4).
- **packing:** OFF (one multi-turn trajectory per sequence); hold the WHOLE trajectory including the terminal edit, filter/front-truncate, never drop the final edit — maxlen truncation trains explore-then-get-cut-off = search-death (dossier §4, §5d item; MEASURED-LOCAL D NULL cause).
- **DoRA / LoRA+:** reserved as experiment #2 / late optimization, each behind a gate and a vLLM-serve-support check (dossier §4).

(d) ANTI-OVERFIT / ANTI-FORGETTING + text overfitting signatures to watch:
- **Replay/anchor data:** mix in replay/anchor trajectories of normal correct tool use (the text analogue of regularization images) so base coding ability is not burned and search-death does not flip into premature wrong-fix (MEASURED/ESTABLISHED catastrophic-forgetting 2308.08747; dossier §3/T10; priors A7 shows wrong-fix already dominates — W=63).
- **Early-stop signal:** 1 epoch + a serve-scale/epoch sweep saving each checkpoint, A/B'd offline (dossier §4, §8 Disagreement C). The real "strength dial" is train-many-save-each + offline-eval-each because vLLM gives no free per-request strength knob (dossier §3 Break #3).
- **TEXT overfitting signatures to watch (name v2 as the cautionary example):**
  - **Serialization key-collapse / malformed `edit_file`** — the C3 signature: `new_string` value followed by literal `` `,old_string: `` so `old_string` becomes a JSON key with a lone-backtick value, rejected "mandatory input parameters are not present: old_string," 11+ times in a repeat-loop (MEASURED C3). This is the autoregressive-grammar failure that has NO image analog (dossier §3 Break #1).
  - **Search-death / behavioral collapse to one action** — tasks making 0 `edit_file` attempts and submitting empty patches (MEASURED C2, 3/5 tasks). Watch edit-attempt rate per epoch/scale.
  - **Dose-dependent degeneration** — a 12B measurement showed tool-call argument collapse emerging at serve-scale 0.75 and severe at 1.0 (MEASURED C4); sweep 0.5/0.75/1.0 to confirm.

(e) PRE-REGISTERED success bar — measured OFFLINE FIRST (dossier §8 shared pre-registration):
- **Judge (held-out):** the dev tasks via `eval_hf_adapter.py` on a **by-task holdout that shares NO tasks with any tuning split, metadata-stripped** (forbidden-list E / accountability rule 8). This offline eval runs BEFORE any Kaggle gate; the FREE Kaggle gate is the next judge and the real LB is the final judge (MEASURED-LOCAL D, F; gemma-submission-protocol).
- **Primary bar (both stages share it):** a lever "moves commitment" iff it raises the edit-attempt rate (fraction of tasks emitting ≥1 `edit_file`) from the measured search-death baseline (**3/5 made 0 edits → edit-attempt rate 2/5**, MEASURED C2) to **≥4/5**, AND does not drop resolves below the v6 baseline (**2/5**, MEASURED C1/A5). Edit-attempt rate is the right proxy because the measured failure is "never calls `edit_file`," observable WITHOUT the hidden pytest.
- **Null to beat:** the no-change v6 decode config at the same budget. Must beat v2's **1/5** resolve and specifically target the commitment-death tasks (rich_4079, rich_4076, rich_3469 — the three that made 0 edits, priors C2).
- **Verdict rule:** if a stage does not clear the bar on the holdout it is a FAILURE reported as such; a null ("decoding did/didn't move it," "LoRA didn't transfer") is a valid result (accountability rules 2, 3). Stage B is attempted ONLY if Stage A misses the bar. Caveat (MEASURED-LOCAL D): local E2B/12B is a weaker localizer than the 31B, so a local MISS on a 31B-localizable task is expected and the local eval ranks changes directionally — a local WIN is a strong positive, used to decide what reaches the FREE gate.

(f) SCORER-GAMING guard (explicit, cite `Gemma\VULN_PUBLIC_TASK_PATCH_STAGING.md`): the harness scores a task SOLELY on whether the produced `git diff` applies and the hidden pytest passes, with NO provenance check (VULN §3), which makes the following FORBIDDEN and baked into neither the adapter nor its data (VULN §1–§4, §6; priors E):
- **No gold patches** — do not ship, stage, or emit the publicly-derivable gold source diff for the exposed public repos (rich / fastapi / requests / httpx) (VULN §2, §4).
- **No problem-statement fingerprints** — no `fingerprint(problem_statement) → gold_diff` map or any mechanism that recognizes a task from its problem-statement text / repo name / file tree and emits a memorized answer (VULN §2, §4).
- **No task-id / dev-answer conditioning** — `instance_id` is not in the prompt (VULN §2); do not condition the adapter or its data on task identity, do not memorize the dev answers. Public tasks are training FUEL (behavioral shape → generalizable priors, metadata STRIPPED at inference), NOT answers to submit; every result must pass the by-task, metadata-stripped holdout (priors E; VULN §6 public/private collapse). The two-key filter keeps only the *shape* of committing, never the content of a fix.

## What the audit must settle

- Is the decoder-first sequencing right for THIS fixed model, or should Stage B run in parallel? The dossier's reconciliation (§2) says falsify decoding first because it is the fastest falsifier AND our own data lit it up (priors §B) — audit whether that evidence is strong enough to gate the GPU spend, or whether the two decode wins (freq_penalty, reserve-tail) were n=1 and need the sweep in rule-13 terms (tune the knob, re-run the motivating diagnostic).
- Does the loss-masking inspection (zero-GPU: assert mean_loss > 0, masked-token count == assistant-turn count, tool-result tokens masked) actually confirm the C3 mechanism before any training run? (dossier §8 Disagreement B.) This is the cheapest falsifier and should run before Stage B.
- Can the training stack reproduce vLLM's W4A16/NF4 object so the QLoRA is trained against the SAME quantization it serves on, or is the bf16-twin → INT4-serve split (train→load→eval PROVEN, MEASURED-LOCAL D) the only feasible path? The dossier (§6) flags the precision/QAT mismatch as UNVERIFIED and says validate on the FREE gate, never assume parity.
- Is the edit-attempt-rate ≥4/5 bar on a 5-task holdout statistically meaningful, or does the holdout need to be widened (shares-no-tasks) before a result is trustworthy? Check against accountability rules 2, 8, 13, 16.
- Round-trip validation: does every candidate training row survive Gemma's own parser with delimiter-bearing values (`,`, `}`, backtick, `\n`) round-tripping byte-equal? A row that fails is a confirmed poison label and must be dropped (dossier §5d).
- Prior art: every adapter/decode config tried (v2 edit-discipline r32; v19 decode levers; v20/v19v3 prompt regressions) with per-task outcomes, so Stage A does not re-run a dead prompt lever (MEASURED-LOCAL A4).

## What could make this ANOTHER null, and how we'd detect it early

- **Decoder already solves it (Stage A clears the bar).** Then the LoRA is unnecessary — this is a SUCCESS for the user's "nudge the model" goal, not a failure, and we stop before spending a GPU cycle. Detected by Stage A's edit-attempt-rate on the holdout (dossier §8 Arm 1).
- **SFT memorizes a few dozen trajectory shapes and does not transfer.** MEASURED/ESTABLISHED risk (SFT memorizes / RL generalizes, Chu 2501.17161; LoRA memorizes at low rank, Biderman 2405.09673). Detected early by the by-task metadata-stripped holdout diverging from the train split (adversarial-validation / rule-8 discipline); if it only works on seen tasks, it is memorization. Mitigation path if it hits: outcome-reward RL rather than more SFT (dossier §2, §8 Disagreement A "both fail").
- **Commit dial overshoots into premature wrong-fix.** Over-refusal analogue (OR-Bench 2405.20947): forcing "commit sooner" can tip search-death into landing a wrong edit. Detected by resolves dropping below the v6 2/5 floor even as edit-attempt rate rises (the bar's AND-clause); wrong-fix already dominates the traced distribution (W=63, priors A7). Mitigation: replay/anchor data + the resolve floor as a hard gate.
- **C3 recurs despite the dict/template fix.** Detected BEFORE training by the round-trip parser gate and the mask inspection (zero-GPU); detected DURING by watching malformed-`edit_file` incidence per epoch/scale and the 0.5/0.75/1.0 dose sweep (dossier §8 Disagreement C).
- **bf16-twin/INT4-serve mismatch silently degrades at serve.** Detected by the FREE gate disagreeing with the offline bf16-twin eval; never assume parity (dossier §6). If the stack can reproduce W4A16, train quant-matched and A/B.
- **Overfitting the 5-task holdout itself.** A ≥4/5 result on five tasks can be noise. Detected by requiring the result to hold on a widened shares-no-tasks confirm split before it is called real (accountability rules 2, 8, 13).
