# PRE-REGISTRATION — A21 compliance-salience arm on 31B, 2026-10-25

Written BEFORE the kernel is pushed or run. Nothing below may be edited after the run starts.

## Question
Does making A3's three success-correlated behaviours literal (get_status example +
patch_size trigger; submit-once example + never-end-empty) raise the resolve rate on
flipping rich tasks, compared with the A3 control — on the real 31B?

## Why this arm (evidence, 129-run compliance analysis, Fisher exact)
- get_status called >=1: 36% solved vs 15% never (p=0.009) — yet 47% NEVER call it, even
  though rule #1 of the prompt is the budget oracle.
- submitted exactly once: 32% vs 7% (p=0.008) — 21 runs never submitted, 7 submitted 2-10x.
- non-empty patch: 33% vs 4% (p=0.001) — 28 runs (22%) ended with zero patch.
- Four content-prompt arms (A18, D2, A19, A20) nulled on E4B. Compliance salience on 31B
  is the untested axis. A3's proven mechanism is a LITERAL EXAMPLE at the point of action
  (the delimiter example), so both substitutions add examples, not exhortations.

## Arms (byte-verified single-span substitutions of the kernel control)
- A3 control: kernel prompt sha 8641826db79b (7505 chars) — the prompt that produced the
  129-run (34/129). Written to prompts/system.md AND system_a3.md by CELL 2.
- A21: sha 25b53c49b417 (7818 chars, +313 / +4.2%). Two substitutions:
  1. budget oracle -> literal get_status call/answer + patch_size trigger;
  2. workflow step 4 -> literal submit_patch answer + never-end-empty check.
  Written to prompts/system_a21.md by CELL 2. Built by prompts/_build_a21.py.

## Design
- Kernel: comfyops/gemma-sibling-conform-31b-a21-arm (private, L4, offline, same
  wheelhouse/competition/model sources as the 129-run kernel).
- Tasks (5): rich_4077 CANARY (18T/0F across all 31B runs), rich_3471 FLIP (4T/10F, the
  task lost between smoke and 129-run), rich_3777 FLIP (4T/1F, flipped in repeat-live),
  rich_4079 FLIP (5T/12F), rich_3278 SOLVABLE (11T/3F).
- REPS=13, ARMS=[A3, A21] -> 130 runs, ~10.3h at the observed ~280s mean; fits one 12h
  session. Blocks alternate (rep, arm); prompt swapped + evaluator rebuilt per block.
- RESUME: rows keyed arm|rep|id in run_rows.jsonl, flushed per run; a crashed session
  continues without repeating runs.
- Traces are per-task filenames (overwritten per rep), so compliance enrichment runs
  IMMEDIATELY after each task, while the trace still holds that run.

## PRIMARY metric
Pooled resolve rate on the 3 flip tasks (3471, 3777, 4079): A21 vs A3, Fisher exact
two-sided, alpha 0.05. Canary and 3278 reported separately, not in the primary.

## GUARDS
1. CANARY: rich_4077 must resolve in >= 60% of A3 runs (8/13). If not, the harness/config
   is suspect and NO arm conclusion is drawn.
2. Mean duration per run must not inflate >20% vs A3.
3. Zero-patch rate must not increase under A21.

## SECONDARY (reported regardless)
- Per-task resolve table (5 tasks x 2 arms).
- Compliance deltas: get_status calls/run, submit calls/run, first_edit_at_call,
  zero-patch rate — does A21 change BEHAVIOUR even if resolves do not move?
- failure_class distribution (RESOLVED / NEVER_LANDED_EDIT / WRONG_FILE /
  RIGHT_FILE_WRONG_CONTENT).

## Honest limits
- n=13/cell: detects only large effects (a 0.3 -> 0.7 swing). A null does not falsify
  salience; it bounds it.
- One session, one seed, one model. Any positive needs a repeat (new session) before the
  submission changes.
- The compliance correlations are observational; this arm tests causality for the
  salience mechanism only.
