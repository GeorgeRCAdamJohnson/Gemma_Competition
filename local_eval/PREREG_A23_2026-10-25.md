# PRE-REGISTRATION — A23 procedural rewrite on 31B, 2026-10-25

Written BEFORE the kernel is pushed or run. Nothing below may be edited after the run starts.

## Question
Does a fully procedural prompt (LOCATE → EDIT → VERIFY → SUBMIT as literal commands,
no rationale, no exhortation) raise the resolve rate vs the control?

## Why this design (the three-win pattern)
Every prompt that ever moved the board was PROCEDURAL — it showed the model the exact
mechanics at the point of action:
  v3 (0.08→0.10): heredoc scratch + edit_file mechanism
  v6 (0.10→0.12): contract-anchoring with literal pytest.raises example
  A3 (0.15→0.18): literal <|"|> delimiter example
Every nulled arm was EXHORTATIVE — it told the model to behave differently or explained why:
  A18, D2, A19, A20 (E4B), A21, A22 (31B) — six nulls, all exhortative or contradiction-cleanup.
A23 is the first full procedural rewrite: every step is a command with expected output;
all rationale, emotional quotes, and behavioral exhortations are deleted.

## What A23 changes vs the control (8641826db79b, 7505 chars)
A23 = 5039 chars (sha 1ce4ac34b0d9, -33.9%). Built as a full restructure, not a
substitution. Verification script confirmed:
  PRESERVED byte-identical: A3 delimiter example + CLOSING DELIMITER warning (A3 win),
    pytest.raises example + input-variants + every-field rules (v6 win), all hard rules.
  NEW procedural sequences: read-before-edit (step 3→5: sed output is source of truth),
    verify-before-submit (step 7: run the one target test, fix once, re-run once),
    one-edit-per-file (step 6), fixed 3-call locate procedure (steps 1-4).
  DELETED: emotional quotes ("prior runs died verbatim"), rationale ("knowing 19 calls
    changes your behaviour"), exhortations ("check constantly", "scope-creep"), A22's
    verbose BudgetExceeded text, the old trigger-table prose, the conform-to-pattern
    prose section (converted to step 4's compare instruction).

## Design
- Kernel: comfyops/gemma-sibling-conform-31b-a23-arm (private, L4x4, same sources).
- Tasks (5): rich_4077 CANARY, rich_3471/3777/4079 FLIPS, rich_3278 solvable.
- REPS=2 -> 20 runs (same as A22; ~1.7h wall, ~6.9 GPU-hours at 4x).
  Quota check at build time; if <7 GPU-hours remain, reduce REPS.
- Blocks alternate (rep, arm); prompt swapped + evaluator rebuilt per block.
- Resume-safe: rows keyed arm|rep|id, flushed per run.
- Incremental arm_summary.json written after every block (survives cancel).

## PRIMARY metric
Pooled resolve rate on the 3 flip tasks (3471/3777/4079): A23 vs A3, Fisher exact
two-sided, alpha 0.05. Canary and 3278 reported separately.

## GUARDS
1. CANARY: rich_4077 resolves in >= 60% of A3 runs. If not, harness suspect, no conclusion.
2. Mean duration must not inflate >20% vs A3.
3. Zero-patch rate must not increase under A23.

## SECONDARY (reported regardless)
- Per-task table (5 x 2).
- Mechanism predictions:
  * read-before-edit: fewer FileEditErrors / anchor-fail runs (edits>0 + patch=0)
  * verify-before-submit: fewer RIGHT_FILE_WRONG_CONTENT (the model catches its own
    wrong fixes before submitting)
  * fixed locate: first_edit_at_call moves earlier (A3 baseline ~15-19)
  * one-edit-per-file: untested (all 5 tasks single-file gold)
- failure_class distribution, behavior deltas (calls, status, reads, duration).

## Honest limits
- n=10/arm: detects only >=45pp effects. A null bounds the idea; it does not falsify
  procedural prompting (the class is 3-for-3 on the board; this is the first test of
  the FULL rewrite).
- One session, one seed. Any positive needs a repeat before submission.
- The prompt is 34% shorter — if it nulls, the cause could be the restructure or the
  missing content, not the procedural style itself. The preserved-wins verification
  mitigates but does not eliminate this.
